## 3. 改动方案

### 改动 1：收尾白名单纳入 `partial`（`continuous_research.py:655-660`）

```python
if (
    _job_is_final(
        str(job.get("status")),
        progress,
        config,
    )
    and progress["total"] > 0
):
    return job, progress, "target_completed"
```

配套新增 `_job_is_final`：

```python
FINAL_JOB_STATUSES = frozenset({"complete", "completed", "success"})

def _job_is_final(status, progress, config):
    fetch = config.get("fetch", {})
    if not fetch.get("finalize_target_on_coverage"):
        # 代码默认关闭：保持 pending == 0 的严格语义（保护合成数据夹具）
        return status in FINAL_JOB_STATUSES and progress["pending"] == 0
    if status not in FINAL_JOB_STATUSES | {"partial"}:
        return False
    return progress["coverage"] >= float(fetch.get("min_universe_coverage", 0.95))
```

### 改动 2：覆盖率阈值**复用** `fetch.min_universe_coverage`，不新造键

**推荐复用**，理由：本次事故的本质是 worker 侧与调度器侧**判据不一致**，
复用同一个键让两侧"按构造保持一致"，以后不会再次漂移。
（若确实需要两侧独立调参，才新增 `fetch.finalize_min_coverage`；默认不这么做。）

### 改动 3：按"生产开启、代码默认关闭"落地

| 位置 | 键 | 值 |
|---|---|---|
| `quant/assistant/config.py` `DEFAULTS["fetch"]` | `finalize_target_on_coverage` | `False`（严格，护住合成夹具） |
| `quant/configs/assistant.yaml` | `fetch.finalize_target_on_coverage` | `true`（生产显式开启） |

阈值不动：生产 `min_universe_coverage: 0.93`（0.9794 ≥ 0.93，留 4.9pp 余量）。
测试里应断言"**生产已显式开启**"，而不是"与 DEFAULTS 相等"。

### 可选加固（P1，建议单独一轮，不混进本次）

把 `:635` 的刹车改成"pending 未下降也计一次"——即把 `pending == 0` 换成
"pending 下降 or gate_failed"。理由：本次闭环之所以能跑 3+ 轮无人刹车，
正是因为该刹车只认 `pending == 0`。这是同一类问题，但改动面更大，建议分次。

  收尾会再次卡在 floor 之下。建议下轮收尾时核对一次实测 coverage，必要时把 floor 降到 0.96。
- **`completion_allow_failed=true` 无上限守卫**：今天 `failed=6`（quarantined，
  `FundNavValidationError` 空响应）放行无所谓；但若源侧大面积故障导致 `failed` 上百，
  收尾会**照过**。这属于 P1 加固（例如 `completion_failed_ratio_cap`），本轮未做。

### 8.6 对 §7.3 末句的更正

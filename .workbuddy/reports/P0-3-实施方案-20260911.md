# P0-3 实施方案：分资产类别发布（分类别 partial 发布）

> 状态：**方案已定，代码未动**。落地时机见 §7 前置条件。
> 依据：`量化系统评估报告-20260911.md` §9.4（原始计划）+ 本轮对代码的逐处核对。
>
> ⚠️ **优先级变更（2026-09-11 23:22）**：新发现 **P0-4「成功轮被误判为失败 → 连败熔断停摆」**
> 正在实际阻断系统（22:05 起已停摆）。**建议先修 P0-4 再修 P0-3**——理由见文末「P0-4」一节。

## 1. 要解决的问题

当前发布是**全有全无**：`research.py:1035` 写 `"published": not failure_reasons`，
`:1130` 只有 `run_status == "success"`（即 `failure_reasons` 为空）才写 `current.json`。
后果：股票模型门槛一失败，已经通过的 ETF / 基金结论被**一并丢弃**，
且界面只能看到"上一份陈旧快照"，无从察觉 ETF/基金其实已就绪。

§9.4 的"第一步"（只暴露就绪度、不改契约）已在本轮完成——`publication` 块已带
`state / ready_asset_types / blocked_asset_types / blocked_reasons`
（`research.py:1016-1053`，本轮实测 `ready=[stock, etf, otc_fund] / blocked=[]`）。
P0-3 要做的就是把这份"可见的就绪度"变成**真实的分类别发布**。

## 2. 目标语义（先定义，再改代码）

| 字段 | 现在 | P0-3 之后 |
|---|---|---|
| `publication.state` | `blocked` / `full` / `partial`（已实现） | 不变，沿用 |
| `publication.published` | `not failure_reasons`（全有全无） | **`bool(ready_asset_types)`** |
| `current.json` 写入条件 | `run_status == "success"` | **`publication["ready_asset_types"]` 非空** |
| 被拦类别的 `asset_paths[t]` | 保留原权重（若组合门槛通过） | **强制 `target_weights={}` / `cash_weight=1.0` / `status="blocked"`** |
| `run.status` | `success` / `failed` | 保留两值，**新增 `"partial"`**（仅当有为被拦类别时） |
| 通知类型 | `research_success` / `research_failure` | 新增 **`research_partial`**（失败类别仍落 `research_failure`） |

**关键安全性质**：`run.status="partial"` 时 `current.json` 必须**只含已就绪类别**的权重，
被拦类别显式归零并标注原因——绝不能把未发布类别的旧权重当成新结论。

## 3. 逐处改动

### 3.1 `quant/assistant/research.py`（核心）

1. **`publication.published`**（`:1035`）→ `bool(ready_asset_types)`。
2. **被拦类别归零**：在 `decision_support["publication"] = publication`（`:1047`）之后、
   写 `current.json` 之前，插入一个循环，照抄 `:986-991` 已有的归零样式：

   ```
   for asset_type in blocked_asset_types:
       decision = decision_support["asset_paths"].get(asset_type)
       if decision is None: continue
       decision["target_weights"] = {}
       decision["cash_weight"] = 1.0
       decision["status"] = "blocked"
       decision["action"] = "不发布（未通过质量/风险门槛）"
       decision["reason"] = "该资产类别未通过门槛，本轮不发布其目标权重。"
   ```
   并把 `decision_support["target_weights"]` 里属于被拦类别的 symbol 剔除
   （symbol→asset_type 映射可用 `:970-974` 的 `combined_types` 同样的构造方式）。

3. **`run_status`**（`:1055`）→ 三态：
   `failed`（`ready` 为空）/ `partial`（有 `blocked`）/ `success`（无 `blocked`）。

4. **写 `current.json` 的条件**（`:1130`）→ `if publication["ready_asset_types"]:`。
   循环保持 atomic_write_json，落盘内容不变（仍写 `decision_support` / `rule_gates`）。

5. **`decision_support["publication_blocked"]`**（`:1057`）语义收紧：
   仅在 `failed`（`ready` 为空）时置 `True`；`partial` 时置 `False` 并保留 `failure_reasons`。

6. **通知**（`:1142` / `:1150`）：三态分派，新增 `research_partial`，
   文案必须显式列出被拦类别与原因。

### 3.2 `quant/assistant/read_api.py:121-138`（MCP 读契约）

`get_current_snapshot` 现直接返回 `current["status"]` 与整个 `decision_support`。
需改为按类别暴露：

- 请求某类别且该类别在 `blocked_asset_types` 中时，`status` 返回
  **`"blocked"`** 而不是继承 `run.status`，并**不返回** `decision_support` 权重
  （照 `:109-120` 已有的 `not_found_or_stale` 分支样式，避免把陈旧权重当新结论）。
- 新鲜度：把 `current.json` 的 `data_end_date` 与请求类别的期望目标日对比，
  落后即标 `stale`（可复用 `:108` 分支的 `not_found_or_stale` 命名习惯）。

### 3.3 `quant/assistant/notifications.py`

新增 `research_partial` 类型常量/允许值（现仅 96 行，改动面小）。同步检查
界面侧对该类型的映射是否 fail-open。

# P0-4 实施方案：成功轮被误判为失败 → 连败熔断停摆

> 状态：**已定位到行号，代码未动**。于 2026-09-11 23:22 核实。

## 1. 事实链（全部有文件/行号证据）

1. **本轮（job `20260911T065625Z-d6d4eede`）实际发布成功**：
   `manifest.json` → `status="success"`、`failure_reasons=[]`、`finished_at=14:05:33Z`；
   `decision_support.publication` → `published=true`、`state="full"`、三类资产全部 `ready`；
   `results/assistant/current.json` → 22:05:33 被更新为 `status=success` 且含全部目标权重。
   ⇒ 按不变量 §7「判断运行成败以 manifest.json / current.json / notifications.json 为准」，**这一轮是成功的**。
2. **但 worker 自报 `status="failed"`**：
   `quant/logs/continuous_research/workers/20260911T065625Z-d6d4eede.stdout.log`
   的 JSON 里 `status="failed"`、`phase="research"`、`error=`：

   ```
   RuntimeError: research process failed: [13824:MainThread](2026-09-11 22:05:24,498) INFO - qlib.Initialization - ...
   [13824:MainThread](2026-09-11 22:05:27,064) INFO - qlib.Initialization - qlib successfully initialized based on client settings.
   ```
   —— 作为"错误详情"的内容**全是 qlib 的 INFO 日志**（qlib 把日志写到 stderr），
   **没有任何 traceback**，看不出真实异常。
3. **判定点在 `scripts/run_research_worker.py:596-624`**（`_run_research_process`）：

   ```
   result = _last_json_object(completed["stdout"])
   if completed["returncode"] not in {0, 1} or result is None:
       detail = completed["stderr"][-1000:] or completed["stdout"][-1000:]
       raise RuntimeError(f"research process failed: {detail}")
   ```
   即：内层子进程 `run_assistant_research.py --queued-run-id <job>` 被判失败，**只依据
   「原始退出码 ∉ {0,1}」或「stdout 解析不出 JSON」**，**完全没有核对产物**
   （`manifest.json` / `current.json`）——这与不变量 §7 的判读纪律相冲突。
4. **异常冒泡路径**：`:1180` 调用 → 抛 `RuntimeError` → `:1221 except Exception` →
   `status_value["status"]="failed"` → `:1220 return 1`。
   外层 worker 退出码 1 → 调度器 `continuous_research.py:1327-1332`
   `round_failed = outcome.returncode not in (0, None) → True`。
5. **熔断触发**：`continuous_research.py:1007-1017` `_record_failure` 累加到
   `failure_streak=3` → `_auto_pause_on_streak` 写 `paused.json`：
   > `automatic pause: continuous research failed for 3 consecutive rounds; job_id=...`
   时间 **22:05:49**。此后每 10 分钟一轮 tick 只写 `phase=paused`，
   **系统从 22:05 起停摆至今**（23:22，近 1.5 小时无产出）。
6. 同一形态在更早的轮次已反复出现（`worker abnormal exit returncode=1`）：
   17:36:47、19:51:36、21:06:43、22:05:49 —— 每次 duration 2959–4821 秒（即整轮研究都跑完了），
   且每次都伴随 `phase=fetch_partial failed_assets=6`。**这不是偶发，而是稳定复现的误判。**

## 2. 尚未定死的一环（修之前需要一次带捕获的复现）

内层子进程为什么返回 `∉ {0,1}` 的退出码，有两种候选：

| 候选 | 支持证据 | 排除方法 |
|---|---|---|
| A. 原生层非零退出（qlib/pyarrow 在解释器 teardown 阶段崩溃） | 错误详情里**只有 INFO 日志、无 traceback**；产物已完整落盘 | 记录内层 returncode 的原始值 |
| B. 内层抛异常 → `run_assistant_research.py:170-178` 打 `{"status":"error",...}` 并 `return 2` | `2 ∉ {0,1}` 正好触发该分支 | 把内层 stdout 落盘，看那行 JSON |

**两种候选的修法相同**（都改为以产物为准），所以不阻塞修复；但定位真因仍需
**把内层子进程的 stdout/stderr 与 returncode 落盘**——现在它只存在于内存里，
每次只能靠猜，这也是本缺陷能潜伏这么久的原因。

## 3. 修法（4 处，均以「产物为准」为原则）

1. **`run_research_worker.py:596-624`**：`RuntimeError` 之前先核对产物。
   若 `<run_dir>/manifest.json` 的 `run_id` 匹配且 `status in {"success"}`，
   （或 `current.json.run_id == job_id`）则**不判失败**：记一条 WARNING（含内层 returncode），
   按成功返回 `result`（必要时用 manifest 重建最小 result 字典：`status/run_id/result_path/error`）。
   只有产物缺失或 manifest 非 success 时才 `raise`。
2. **同处**：错误详情改为「returncode=… + stderr 末 1000 字」，
   并把内层 stdout/stderr 追加落盘到
   `quant/logs/continuous_research/workers/<job_id>.research.std{out,err}.log`，
   使候选 A/B 下次可判。
3. **`continuous_research.py:1327-1332`**：`round_failed` 增加一条否定条件——
   当本轮 `manifest.publication.published` 为真（或 job 状态为 `complete`/`partial`）时，
   即使 worker 退出码非 0 也不计入 `failure_streak`，只记 WARNING。
   **注意：`_auto_pause_on_streak`（2026-09-10「防空转B」）是刻意的守卫，必须保留**——
   要修的是**误判**，不是削弱熔断。
4. **`data_quality_failure` 关键词判定**（`:1323-1326`）：
   `"gate"` / `"model"` / `"quality"` 这类子串匹配会把正常日志（如 `model gate` 类文案）
   误判为数据质量失败，建议改为读结构化状态而非文本匹配（与不变量 §7「待做」同源）。

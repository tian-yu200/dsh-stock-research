# 研究管线不变量（agent 必读）

> 本文件记录 2026-09-05 全市场研究链路大修中被实证的**不变量与禁忌**。
> 每条规则后面是它背后的事故证据——不要在没有重新验证证据的情况下"简化"、"优化"或"重构"这些设计。
> 违反这些规则的修改曾经分别导致：900+ 标的卡死一整天、全市场扫描 9 小时跑不完、模型 OOM。

## 1. 市场前缀与数据源映射（`data_source.py::_market_prefix`）

- **920 段是北交所，必须映射 `bj`**（新浪 hfq 通道依赖它）。
- **同花顺 v6 接口把 920 代码放在 `hs_` 命名空间**（`bj_` 前缀 404），`/02/` 段才是后复权，金额单位是元。
- 腾讯接口解析不了北交所载荷（KeyError）；新浪支持 `bj` 前缀 hfq；东财（push2his）对本机长期反爬（ConnectionError）。
- 数据源顺序即容灾顺序：东财→腾讯→新浪→（仅 920 追加）同花顺。**不要调整顺序或删除兜底源。**

## 2. 熔断与重试（`data_source.py` / `fetch_stock_data.py`）

- `_SOURCE_BREAKER_THRESHOLD = 20`：一个源连续 20 次同类型异常后，本进程内跳过。删除熔断 = 每个标的都先撞一次反爬（曾与其它因素叠加导致 worker 预算黑洞）。
- `_DETERMINISTIC_EXCEPTIONS`（AttributeError/KeyError/TypeError/IndexError）**跳过秒级退避重试**：解析类异常秒级重试不会改变结果，只会烧预算。瞬时网络异常仍走完整退避，不要合并这两类。
- `RuntimeError("...所有数据源均失败...")` 必须携带 `failure_class="all_sources_failed"`（状态库按类重放依赖它）。

## 3. 数据质量防线（`market_data.py` / `price_guards.py`）

- `normalize_daily_bars` **丢弃非正价格行**并记入 `field_anomalies`：新浪历史里存在价格全 0 的行（改码前旧数据），0 价格会产生 -100% 假收益毒化模型。实证：34 个文件 185 行。
- `normalize_daily_bars` 的去重排序**必须是稳定排序**（`sort_values("date", kind="stable")`）：同日期重复行靠拼接顺序 + `keep="last"` 确定性地保留新行；快速排序对重复键次序不稳定，增量修订会被随机丢弃。
- `validate_daily_bars` 已**数组化重写（约 29 倍提速，A/B 零差异）**。严禁改回 `work.loc[i]` 逐行 pandas 访问——单标的 1-2.6 秒 × 31k 标的 = 扫描 9 小时。
- `validate_daily_bars` 的跳变检测有**两条腿**：开盘对前收盘（主路径）+ **开盘缺失（open=0/NaN，注意 NaN 是 truthy，用 `o != o` 判）时的 close-to-close 退化分支**（`close_jump_scale_break`）。新浪通道的 open 缺失形态曾让第一条腿完全失效（`abs(NaN) > thr` 恒 False）。停牌复牌（>10 自然日）两条腿都豁免。
- `fetch_utils.assert_basis_continuity`（**拼接基准连续性守卫**）：`merge_daily_frames` 写盘前校验边界台阶（相邻 close 比值超出 [1/1.5, 1.5]）与重叠日期中位偏离（>10%），断裂抛 `BaselineDiscontinuityError`；worker（stock 与 fund/ETF 两条路径）捕获后把 CSV 挪开 `.discont.bak` 并**降级同源全量重取**，失败则还原现场。不要为省一次全量抓取绕过它。
- 修改守卫语义前必须先跑 A/B 对比，黄金基线：`quant/logs/codex-runs/price-guard-golden.pkl`（4 帧，含跳空拦截/除权确认/停牌复牌/NaN 分支），输出必须零差异。

## 3b. 滚动初选防线（`assistant/rolling_scan.py`，2026-09-05 毒分数事故后增设）

- **事故档案**：9-02/9-03 跨源复权基准拼接（~3 元历史 + ~200 元新行）产出 499 条毒分数（如 600654 r20=31756%、年化波动 65706%）。9-04 CSV 修复后毒分数仍复读多日，因为旧重算判定只比较 data_end_date，认不出"同末日期、内容被重写"。
- **重算判定 = 内容指纹**：`data_end_date + rows + source`（fetch_state.assets 三列现成）任一变化即重算（`_fingerprint_changed`）。NULL 侧不参与比较（错误记录不能进永久重算循环）。不要"简化"回单比 end_date。
- **物理合理性门槛**（`_rank_one_type`）：|r20|、|r60| > `max_abs_return_20d/60d`（默认 1.5）或 60 日年化波动 > `max_volatility_60d`（默认 3.0）→ 判不合格。后复权日线出现这种数值几乎必然是基准断裂残留，不是趋势机会。
- **交易日滞后分层**：快照 `freshness` 按 data_end_date 相对全市场基准日（池内类型最大 end_date）分 6 层（当日/1/2/3-4/5+/缺失）；**落后 ≥ `max_trading_lag_days`（默认 2）个交易日的标的踢出海选池**。滞后用本地交易日历缓存（`data/benchmarks/trade_calendar.csv`，只读不联网）计算；缓存缺失退化为观测日期集合近似——分层会偏乐观，属已知局限。
- 清理毒分数的标准动作：先备份到 `quant/logs/codex-runs/poisoned-scores-backup-*.json`，再 `DELETE FROM scores WHERE return_20d > 5`，下一轮 pass 自动重算（499 < 800/波上限，一波完成）。

## 5. 内存约束（16GB 物理内存，空闲约 4.7GB）

- **全历史（2020 起）Alpha158 特征矩阵 = 7.8M 行 = 4.59 GiB 单块分配，必然 MemoryError**。训练窗口 2023→2026（约 2.4 GiB）是经计算得出的可行解，不要为"更多历史数据"改回长窗口，除非先解决内存（分块/磁盘缓存/更大机器）。
- `research.py` 模型阶段前的 `all_frames.clear(); gc.collect()` 不能删：信号算完后行情帧不再使用，释放它们是模型阶段能在 16GB 上存活的前提。

## 6. 海选原则与门槛语义（`research.py` / `configs/assistant.yaml`）

- `require_full_universe_for_weights: true`：**定向研究（指定 symbols）只输出信号与门槛，不产生买入权重**——它因 `full_universe_screen_passed=false` 而整体 failed 是设计行为，不是 bug，不要"修复"它。
- `stock_label_horizon: 20` = 模型预测未来 20 个交易日相对收益 = 系统隐含持有期，改它等于改交易语义。
- **类别内** 12 项门槛一票否决：任何一项 false，该资产类别即不发布（cash/observe 是正确行为，
  不是需要绕过的问题）。
  ⚠️ 2026-09-11 整改(**P0-3**) 反转了此前的"发布是全有全无"契约：**类别之间独立发布**——
  只要还有类别就绪就写 `current.json`；被拦类别权重归零、在 `publication.blocked_asset_types`
  / `blocked_reasons` 里标注，且经只读 API 查询时返回 `blocked` 而不带 `decision_support`；
  `run.status` 变为三态 `success`/`partial`/`failed`；通知类型新增 `research_partial`。
  **不要**把 `partial` 当失败（那正是 P0-4 的误判形态），也不要为"统一"退回全有全无。

## 7. 任务台账与断点

- job 状态机：queued → running → complete/timeout/failed。timeout/failed 由调度器 tick（约 10 分钟一轮 `--action once`）自动 requeue 续跑，**断点有效**（fetch/Qlib 走指纹缓存）。
- **收盘后数据保鲜（`--action postclose`，计划任务 `\DSH-股票助手\收盘后数据更新`，周一至周五 17:30）**：24 小时刷新计时器与收盘不对齐——在数据源发布当日 K 线前抓到"确认无新数据"的标的会再睡满一个周期，滞后逐日复利（界面侧只能把滞后标的踢出海选，见 3b）。postclose 把 data_end_date 落后最新交易日的成功标的**强制到期**（`FetchState.advance_due_for_stale`，不动租约在途/失败行），然后 `run_once` 重跑研究；全市场已最新时自动跳过（省 1.5-2 小时）。不要"优化"掉强制到期这一步——只调 refresh_interval 治不了 verified-empty 的空转。
- **已知误报**：job 台账的 `last_error` 可能把 worker stderr 里的正常日志（git CRLF 警告、qlib 可选模型提示、LightGBM 训练日志）误判为失败文本。**判断运行成败以 manifest.json / current.json / notifications.json 为准，不要以 jobs.last_error 为准**，也不要据此"修复"研究进程。
- 重活一律遵守 `AGENTS.md` 的分离进程规范（Start-Process / DETACHED_PROCESS、日志落 `quant/logs/codex-runs/`、记录 PID 与 exit 文件）。
- ⚠️ **退出码不是成败判据（2026-09-11 P0-4 事故）**：`run_research_worker.py` 的
  `_run_research_process` 原先只看内层子进程的原始退出码（`not in {0,1}`）与 stdout 能否解析出
  JSON。job `20260911T065625Z-d6d4eede` 已成功发布（manifest success、`current.json` 22:05:33
  更新、`publication.state=full`），内层却返回异常退出码，于是被记为失败 →
  `failure_streak` 累到 3 → `_auto_pause_on_streak` 在 22:05:49 把整个调度器停摆。
  该形态当天稳定复现（17:36 / 19:51 / 21:06 / 22:05，每轮 duration 约 50–80 分钟即整轮都跑完了）。
  **现在**：`_run_research_process` 判失败前先核对产物（`_published_research_result`，含
  "finished_at 不早于本次调用"的新鲜度守卫，防止复用 run 目录时读到上一次 pass 的旧成功产物）；
  调度器 `continuous_research.py::_round_published` 同样以 `manifest.publication.published` 为准。
  **`_auto_pause_on_streak`（2026-09-10「防空转B」）是刻意守卫，只修误判，不要削弱熔断。**
  内层子进程的 stdout/stderr 现落盘到 `logs/continuous_research/workers/<job_id>.research.std{out,err}.log`
  （原先只在临时文件里、退出即删，导致真因无法判定）。
  **教训**：任何"判成败"的地方都必须读 `manifest.json` / `current.json`，不要读退出码或台账文本。
- ⚠️ **"已发布"必须包含 `partial`（2026-09-13 复核补漏）**：P0-3 之后 `manifest.status` /
  `current.json.status` 是三态 `success`/`partial`/`failed`，其中 `partial` = 至少一个资产类别
  已发布（被拦类别权重已归零并标注）。任何"本轮是否已发布/是否完成"的判据都必须认 `partial`，
  否则 partial 轮会被当成未完成或失败，重新制造 P0-4 那类误判。
  本次复核找到两处仍是 `== "success"` 的遗漏并已同步：`fullscan_guardian.py::tick` 的
  completion 判据（原判据会让 partial 轮不写 DONE_FLAG、不自我注销计划任务，监护语义失效）、
  `check_research_evidence.py` 的"最后一次已发布运行"汇总。
  **注意三个同名 `partial` 语义不同，不要互相当作判据**：
  ① `run.status=partial` = 分类别发布（本条约），落在 `manifest.status` / `current.json.status`；
  ② worker `status.json.status=partial` = 数据未抓全但研究已发布（见 `run_research_worker.main`）；
  ③ **job 创建态**的 `partial`（见 `continuous_research._ensure_job`）——与发布无关。
- ⚠️ **监护的 DONE_FLAG 是全局单文件，必须按 job_id 比对（2026-09-13 评审补漏）**：
  `fullscan_guardian.py` 的 `DONE_FLAG`（`logs/codex-runs/fullscan-guardian/guardian-done.json`）
  **不按 job_id 隔离**。`tick()` 原先只判"文件是否存在"就短路返回 completed，于是上一轮残留的
  done flag 会让**重新注册**的监护每次 tick 都短路：既不巡检 `paused.json`、也不 resume
  瞬时暂停 → 表现为"任务在、日志看着正常、监护却已静默失效"，**比没有监护更危险**。
  现判据为 `done.job_id == latest.job_id` 才采信；stale flag 忽略并继续巡检。
  **同源禁忌**：无在跑作业时（`latest_status` 的 `job_id`/`run_id` 为空——非交易日 `status`
  同样是 `"paused"`）不得走 anomaly 分支，那会判 `paused-transient` → 每 5 分钟调一次
  `resume()` 并写一个 diagnosis 产物（2026-09-10~11 实测堆了 12 个 `paused-transient` 文件）。
  现 `job_id` 为空即判 `idle` 直接返回，不介入。
  回归测试：`quant/tests/test_fullscan_guardian.py`（旧逻辑下 3 failed / 1 passed）。
  ⚠️ 监护是**绑单轮作业**的：每轮开始都要 `tasks/register-fullscan-guardian-task.ps1` 重新注册，
  作业完成后它会自注销。
- ⚠️ **收尾门 ≠ 放行门；判据放宽必须与 DB 终态写入成对出现（2026-09-15 整改）**：
  `_ensure_job` 原先要求 `job.status ∈ {complete,completed,success}` **且** `progress["pending"] == 0`
  才判 `target_completed`。两个合取项**在实践中同时不可达**（注意：不是字面死循环——
  `run_research_worker` 在三量全零时确实会自写 `complete`）：
  ① DB 的 `job.status` 常年是 `running`（worker 启动即写回，每轮结束才短暂落 `partial`，
     而调度 tick 约 10 分钟、几乎总撞上飞行中的 worker）；
  ② `pending` 极少归零——QDII/货币基金净值滞后 + 退市死代码把覆盖率长期压在 ~97.9%
     （见 `configs/assistant.yaml` 中 `min_universe_coverage` 的注释，那里已记录过同类事实）。
  实测 2026-09-15：`pending=604 / coverage=0.9794` 冻结约 3 小时，`target_date` 停在 09-14，
  新交易日永远排不上队。
  **现判据**改为基于 `progress`（`_job_progress` 每次现场重算，独立于 DB 状态）的覆盖率：
  `coverage >= fetch.completion_coverage_floor` 且（`failed == 0` 或 `fetch.completion_allow_failed`）。
  DEFAULTS 为 `1.0 / False`（⟺ 原 `pending == 0`），生产 `assistant.yaml` 为 `0.975 / true`。
  ⚠️ **两条纪律**：
  ① `completion_coverage_floor`（收尾门，决定"这一天能否算收尾、轮到下一交易日"）与
     `min_universe_coverage`（放行门，决定"数据够不够发布"）语义不同，**不要混用、不要合并**；
  ② **判据放宽必须与 `target_completed` 分支的 DB 终态写入成对出现**——该分支原先只写
     `latest_status.json` 就 return、不动 DB 行。`RESUMABLE_JOB_STATUSES =
     {"queued","partial","running"}` 不含 `completed`，所以必须
     `update_job(status="completed", ...)` 才能让下一 tick 的 `_find_resumable_job` 跳过它、
     走到 calendar 分支用当日日期建新作业。**只放行判据不写终态 = 死循环从"忙等"变成"闲等"。**
  **写终态时的三个坑**（均有实证）：`coverage/failed/pending` 只能从 `progress` 现场取
  （`_ensure_job` 内的同名局部变量不在调用方作用域）；`finished_at` 必须传
  `_now().isoformat()` 字符串（库内时间列全是 ISO 文本、`update_job_if` 的 CAS 是字符串比对）；
  豁免清单进 `metadata` 而非 `last_error`（后者非空在全 repo 惯例里表示失败），
  且 `update_job` 的 `metadata=` 是**整包替换**，必须先 `dict(_job_metadata(job))` 再 update，
  否则会擦掉 `target_date` / `asset_types` / `asset_scope` / `symbols`。
  回归测试：`tests/test_continuous_research.py::test_coverage_floor_closes_target_and_writes_terminal_job_state`
  与 `::test_coverage_floor_is_strict_by_default`。

## 10. 宁缺毋滥过滤器（`research.py::_pool_quality_filter`）

- **生产开启、代码默认关闭**：`configs/assistant.yaml` 显式设置 `pool_exclude_st: true` / `min_listing_age_calendar_days: 90` / `min_avg_amount_20d: 10000000` / `pool_exclude_cross_border: true`；`config.py::DEFAULTS` 保持关闭——测试夹具（tests/fixtures/research_snapshot）使用合成低成交额数据，默认开启会破坏快照测试。
- **四类剔除**：ST/*ST/退市整理（名称）、次新（上市不满 90 日历日）、低流动性（20 日均成交额 < 1000 万）、跨境（名称含境外市场关键词：标普/纳指/恒生/沪港深/全球/海外等——用户规则：不配美股港股敞口，2026-09-06 起）。
- **对股票和 ETF/基金双路径生效**：个股在 qlib 排名后、top-k 前；ETF/基金在 trend_score 候选截断前（candidates[:2] 之前）。
- 过滤发生在**打分后、取 top-k 前**：模型信号列表保持完整（透明可查），被剔除的候选不进权重表；剔除明细写入 run 的 `logs/research.log`（`[宁缺毋滥] ...`）。
- 过滤器 fail-open：缺 name/start_date/liquidity 的候选按合格处理。

## 10.1 源头排除（2026-09-07 美股港股不计入统计）
